## 1. 目的与判据

验证 §4.1.1 依赖的四项底层能力在真机上的实际表现，并产出 §3.3 延迟预算与 §3.4 抖动缓冲的参数：

| # | 能力 | 通过判据 |
|---|---|---|
| C1 | `RecorderManager` PCM 分片（`frameSize`）稳定回调 | 持续 ≥60 s，**分片最大间隔 < 200 ms**（页面「分片间隔」为绿色） |
| C2 | `WebAudioContext` 连续调度播放 | 30 s 连续回放有欠载率数据；目标欠载率 < 1%，且主观无明显断续/爆音 |
| C3 | 单条 WS 同时承载二进制音频与 JSON 文本 | 5 分钟内无断线；音频持续时 JSON 往返（cmd）最大值 < 300 ms；心跳 15 s 无超时 |
| C4 | 后台/中断行为 | 切后台、锁屏、来电各一次，行为有记录（WS 是否存活、录音是否中断、能否恢复、需什么动作恢复） |

## 2. 准备

### 2.1 人员与设备

- 测试人员 1 名（持机），协助 1 名（用另一部手机给被测机打电话/发微信语音）。
- **iOS ≥1 台、Android ≥1 台（目标各 2 台，Android 尽量覆盖两个不同厂商）**。机型、系统版本、微信版本、基础库版本由页面顶部「环境」行和复制出的报告自动给出，仍请在记录表里手填一遍作核对。
- 微信 ≥ 8.0.x 且支持基础库 ≥ 2.27.3。

### 2.2 电脑侧（执行人：A-2 或业主侧工程师）

1. 安装并登录**微信开发者工具**（owner-actions：需业主本人安装/登录；测试号即可，无需企业认证）。
2. `pnpm install`；`pnpm --filter @railvoice/miniprogram build`。
3. 启动回声服务（手机与电脑同一局域网，放行 8787 端口）：
   - 常规：`pnpm --filter @railvoice/ws-echo start`
   - 弱网（模拟 4G 抖动）：`pnpm --filter @railvoice/ws-echo start -- --delay-ms 80 --jitter-ms 60 --drop-pct 1`
4. 开发者工具导入 `apps/miniprogram`（AppID 用测试号），点「真机调试」或「预览」扫码；手机上右上角「…」→「打开调试」。
5. 页面「WS 地址」填 `ws://<电脑局域网IP>:8787`。其余细节见 `tools/ws-echo/README.md`。

### 2.3 手机侧

- 首次点「开始」授权麦克风。
- 音量调到中等；**先用耳机或外放离麦克风 ≥30 cm**，避免回声自激（回放会被麦克风再次录入）。回声测试建议用耳机。
- 关闭省电模式，保持屏幕常亮（S4 之外的场景）。

### 2.4 页面指标说明

| 页面项 | 含义 |
|---|---|
| 分片间隔 均值/最大 | 相邻两次 `onFrameRecorded` 回调的时间差；**判 C1** |
| 上行 | 近 1 s 上行字节率；已发/静音跳过帧数（本地能量阈值判静音时不发包） |
| 下行(echo) | 回声帧的 seq 统计：收到/丢/乱序/重复 |
| 播放欠载 | 「欠载次数 / 已调度块数」：下一块到达时上一块已播完，需要重新预缓冲 |
| 音频往返 | 发出一帧到收到其回声帧的时间差（含服务端延迟注入） |
| JSON 往返 | 心跳 `ping→pong` 与模拟 `cmd.submit→cmd.state` 的往返，音频同时在跑 |
| 事件 | 时间线：开始/停止、后台/前台（含后台期间收到的分片数、WS 状态）、录音中断、录音停止（60 s 自动重启）、停顿（>500 ms 无分片）、错误 |

页面「复制报告」把环境、配置、全部指标和事件时间线复制为 JSON（已去掉 URL 中的凭据与查询串）。**每个场景结束后点一次，贴到记录表对应行的「报告」列或另存文件。**

## 3. 场景与步骤

每个场景开始前点「清零统计」；除特别说明外：录音源=麦克风，frameSize=2 KB，抖动缓冲=160 ms，静音不发包=关（保证持续有数据），中断处理=不处理。**说话内容：对着手机连续念数字或读一段文字（保持有声）。**

### S1 分片间隔稳定性（C1）

1. frameSize 依次选 **1 KB、2 KB、4 KB**，每档连续说话 60 s。
2. 抄录：分片间隔均值/最大、上行字节率、是否出现「停顿」事件。
3. 期望：间隔均值≈32/64/128 ms；最大 < 200 ms。

### S2 30 秒连续回放（C2，决定抖动缓冲）

1. 回声服务用**常规**与**弱网**两种配置各做一轮。
2. 每轮对抖动缓冲 **120 / 160 / 200 ms** 各跑 30 s（耳机；连续说话）。
3. 抄录：播放欠载「次数/块数」、音频往返均值/最大、下行丢/乱序、主观评价（顺畅/偶尔断续/严重断续/爆音）。

### S3 单 WS 多路复用（C3）

1. 在 S2 的任一轮里同时观察「JSON 往返」；再单独跑一轮 **5 分钟**（frameSize 2 KB，抖动 160 ms，静音不发包=开，说话/停顿交替）。
2. 抄录：JSON 往返 ping/cmd 的均值/最大、是否断线（事件里有 `socket-close`/`socket-error` 即记）、心跳是否持续。
3. 期望：音频持续时 cmd 最大 < 300 ms，无断线。

### S4 后台/锁屏（C4）

录音进行中（说话），依次：

1. 按 Home 回桌面，**10 s** 后切回。
2. 锁屏 **10 s** 后解锁回到小程序。
3. 切到另一个 App（如微信聊天），**10 s** 后切回。
4. 抄录每步事件里 `hide`/`show` 行（`awayMs`、`ws=`、`framesWhileHidden=`）；回来后是否仍有分片（「分片间隔」是否继续增长）；回放是否继续；是否需要点「停止/开始」才能恢复。

### S5 中断（来电）（C4）

1. 中断处理选「不处理」：开始录音后用协助手机拨打被测机（或发微信语音通话），**响铃 5 s 后挂断/拒接**。
2. 抄录事件：`interruption-begin`/`interruption-end` 是否出现、之后是否继续收到分片。
3. 若中断后录音没有自动恢复：重复一轮，分别选「中断后 start()」「中断后 resume()」，记录哪种能恢复及恢复耗时。
4. 再做一轮**接听**通话 10 s 后挂断，同样记录。

### S6 60 s 时长上限

1. 连续录音 **≥ 90 s**。页面在 `onStop`（到达 `duration:60000`）时自动重新 `start`。
2. 抄录：`recorder-stop` 事件时刻、紧随其后「停顿」事件的间隔毫秒数（重启造成的缺口），以及缺口前后是否丢音。

### S7（可选）30 分钟浸泡

静音不发包=开，frameSize 2 KB，保持屏幕常亮，间歇说话 30 min。抄录：是否断线、上行总包数、发热/耗电主观感受、欠载累计。

### S8（可选）网络切换

Wi-Fi → 4G 中途切换（需回声服务可从公网/隧道访问，或用手机热点反向连电脑）。抄录断线事件与是否需要手动重连（本 Spike 不自动重连，用于评估 §6.2 重连策略）。

## 7. 对 §3.3 / §3.4 的结论与建议

> 状态：**设计推演（待真机数据确认）**。凡标「待数据」处，以第 4 节实测为准；结论定稿后删除本提示。

### 7.1 `frameSize` 与网关是否需要重切帧（可由算术确定）

- `RecorderManager.frameSize` 的单位是 **KB（1 KB = 1024 B）**，PCM16 单声道 16 kHz 每秒 32000 B。可选整数 KB 对应时长：1 KB = 32 ms，2 KB = 64 ms，4 KB = 128 ms。
- 需求/讯飞侧要求的 **1280 B / 40 ms** = 1.25 KB，**无法由小程序直接产出**。
- **结论：网关必须把小程序上传的分片重新切成 1280 B/40 ms 再转发讯飞**（含 VAD 尾帧的残余缓冲与 `flags` 末帧标志的处理）。这是确定结论，与真机数据无关。
- 建议默认 `frameSize = 2`（64 ms）：抖动容忍与 WS 帧开销之间的折中；1 KB 可降低 32 ms 采集延迟但包速率翻倍（≈31 包/s），是否值得由 S1 的间隔稳定性与耗电决定（**待数据**）。

### 7.2 对 §3.3 延迟预算的影响

- 小程序采集侧延迟≈**一个 frameSize 时长**（2 KB 时 64 ms，高于需求书 40 ms 假设）；该项应计入 §3.3「小程序最后一帧上传」的 150 ms 预算（仍在余量内：64 + 上传 80 ≈ 144 ms）。**若 S1 实测最大间隔逼近 200 ms，则该项预算需上调（待数据）**。
- 网关重切帧是内存操作，≤1 ms，可忽略。

### 7.3 对 §3.4 抖动缓冲的建议

- 起始值取 **160 ms**（计划区间 120～200 ms 的中值）。
- 选值规则：在「弱网」配置下，取使 30 s 欠载率 < 1% 的**最小**缓冲；若 200 ms 仍不达标，则说明网络抖动已超出方案 C 假设，需要评估增大缓冲到 300 ms 或启用丢包补偿（待数据）。
- 方案 C 延迟估算（§3.4）中「抖动缓冲 150 ms」项按最终选值更新；总延迟仍应 ≪1 s。
