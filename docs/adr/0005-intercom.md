## 0. 结论摘要（先看这里）

1. **D-05 基线不变**：Phase 1～2 做方案 C（自建半双工 PTT，经云端网关中继）。它是唯一不依赖小程序类目、第三方账号与公网厂商云的方案，且能满足录音、转写、审计与铁路专网私有化（D-10）。
2. **方案 B（TRTC 全双工）是「双重门禁」的条件项**：小程序侧要求企业主体 + 从有限类目表中选对类目并自助开通；狗端侧公开资料里的 Linux SDK 是**需申请的「服务端 SDK」**，前置条件是购买 **旗舰版及以上**包月套餐（6,250 元/月，按年约 75,000 元），aarch64 与设备端授权方式**公开资料未写明** ⚠️，须向腾讯云确认（问题清单见 [0005-appendix-tencent-questions.md](./0005-appendix-tencent-questions.md)）。
3. **方案 A（微信设备音视频通话）比策划书写的更可行，但语义不同**：微信已发布「小程序音视频通话 SDK（Linux）」，官方文档给出 arm64 工具链要求，所以策划书 §3.4 中「Jetson/Linux 侧集成路径不明确 → 仅当加装 Android 计算板」这条**已过时**。但它是 1 对 1「来电」语义（授权、响铃、接听），必须接入类目「工具—设备管理」、营业执照经营范围含硬件设备销售、提交视频与寄送实体设备审核，且媒体走微信后台，云端网关拿不到音频 → 与「全程可录音、可转写、可审计」冲突（🔸推断，见 §3）。
4. **策划书 §4.4.2 中给业主的类目建议「工具 → 办公/效率」不在 live-pusher / live-player 的开放类目表里**（S1、S2）。已在 `docs/owner-actions.md` B-3/B-5 修正为：基线与方案 A 选「工具 > 设备管理」，方案 B 的候选类目是「IT科技 > 多方通信 / 音视频设备」，并要求类目必须与真实业务相符（S15 §2.5.7、§2.5.15）。
5. **升级触发条件**见 §4.2；**阶段 2 的开通尝试与结果记录模板**见 §5。

### 2.3 微信「设备音视频通话」— 方案 A

| 项 | 核验结果 | 来源 |
|---|---|---|
| 授权 API | `wx.requestDeviceVoIP`：基础库 2.27.3 起；参数 `sn`（≤128 字节，仅数字/字母/下划线/连字符）、`snTicket`（5 分钟有效）、`modelId`、`deviceName`（≤13）；设备组模式 `isGroup` + `groupId`（2.30.4）；不支持小程序插件 | ✅ S7 |
| 接入形态 | 三种：安卓 WMPF 直连、**Linux SDK 直连**、云对云（低功耗 Linux/RTOS）；「每台设备只能绑定一个小程序，只能和一个小程序进行通话」；仅 1 对 1；微信客户端 ≥ 8.0.30；通话流程**不支持开发者工具，须真机** | ✅ S8 |
| Linux SDK 设备要求 | arm64 工具链「gcc-linaro 7.3.1 及以上（glibc 2.17, glibcxx 3.4.22）」；C++14 的 `libstdc++.so.6`；`libcurl` ≥ 7.84.0；麦克风/扬声器需 16 kHz PCM；推荐双核 500 MHz、64 MB 内存；系统时间必须正确；**必须接入微信官方拨打铃声，否则无法通过 VoIP 接入审核**；需实现硬件抽象层 | ✅ S9 |
| 通话语义 | 设备可呼叫手机微信（`wx_voip_session_call`），手机微信也可呼叫设备（`wx_voip_listener_join`）；被叫用户必须先在小程序内用 `wx.requestDeviceVoIP` 授权该设备；设备注册后只能给注册时绑定的那一个小程序拨打 | ✅ S8、S9 |
| 平台门槛 | ① 「经过微信认证的非个人主体小程序」；② 类目「**工具—设备管理**」并在后台「功能 › 硬件设备」开通、添加设备类型、取得 `model_id`；③ 营业执照经营范围包括硬件设备销售等；④ 「验证小程序音视频能力」：**视频验证 + 寄送实体设备**到微信团队；⑤ 一个小程序最多 5 个服务类目 | ✅ S10、S11、S12 |
| Linux 路径 | 开放平台账号与微信终端合作平台（wecooper）账号的注册**仅安卓直连需要，Linux 设备不需要** | ✅ S11 |
| 设备唯一性 | 要求 eMMC 存储分区写入不可更改的唯一 key；SDK 要求「若设备包含 RPMB，则必须确保 RPMB 分区未被使用」。Go2 EDU / X30 机载 Orin NX 的存储形态是否满足，需 A-3 确认 | ✅ S9、S11 / ⚠️ 本项目设备 |
| 费用 | 开通后可得 10 个 7 天有效期的体验 license；之后需购买「设备 license 套餐」（A～E 五类）。同一社区帖下有开发者留言称「不用购买了」，**不是官方答复** | ✅ S11 / ⚠️ 现行收费规则 |
| 失败信号 | `wx_voip_session_call` 返回 `WXERROR_UNAVAILABLE`：小程序未开通 VoIP 权限、通话时长不足或设备未购买 LICENSE | ✅ S9 |
| 审核要求 | 视频验证（开机流程、手机端授权/接听录屏、设备端拨打/通话录屏）+ 寄送设备（需完整实体设备、电源线、开机说明、体验权限、设备上标注公司/小程序名/AppID/型号）；VoIP 界面占屏 ≥ 1/2、不得含广告 | ✅ S12 |
| 与 `wx.joinVoIPChat` / `wx.join1v1Chat` 的区别 | 这两个是「小程序用户 ↔ 小程序用户」的通话：`joinVoIPChat` 可在接口设置自助开通，最多 10 人/房间；`join1v1Chat` 限定类目。**狗不是小程序用户**，因此都不能当作狗端对讲方案 | ✅ S16、S17 |

## 3. 三方案对比

| 维度 | **方案 C：自建半双工 PTT（基线）** | **方案 B：TRTC 全双工** | **方案 A：微信设备音视频通话** |
|---|---|---|---|
| 用户体验 | 半双工：同一时刻一方说话（符合对讲机习惯，不是需求书字面的 WebRTC） | 全双工 | 全双工 1 对 1「来电」：授权、响铃、接听、挂断（微信统一界面） |
| 小程序侧资格 | 无特殊接口权限；需 `scope.record` | **企业主体**（S3）+ 开放类目表内的类目（S1/S2）+ 接口设置自助开通；测试号不可用；仅真机 | **认证的非个人主体**（S10）+ 类目「工具—设备管理」+ 经营范围含硬件设备销售（S11）+ 设备能力审核（视频 + 寄送实体设备，S12） |
| 资质风险 | **低**。无类目依赖 | **高**。可对应的类目只有「IT科技 › 多方通信；音视频设备」，所需资质未核验 ⚠️；类目与业务不符属违规（S15 §2.5.7）；RK-01 在此 | **中**。类目门槛低于 B，但需实物审核；设备唯一性（eMMC/RPMB）与本项目机载计算单元的匹配未知 ⚠️ |
| 狗端集成 | `dog_intercom`（Python `websockets` + Opus）；全部自研可控 | Linux SDK 为「服务端 SDK」，须申请且前置旗舰版套餐；**aarch64、授权方式未公开 ⚠️**；非「C 语言设备端 SDK」 | 微信 Linux SDK（arm64 工具链，C++14，需实现 HAL、接入官方铃声）；SDK 包需登录下载，未实物核验 ⚠️ |
| 延迟 | 估算 ≈ 400 ms（策划书 §3.4：采集 40 + 上传 80 + 中继 10 + 下发 80 + 抖动缓冲 150 + 播放 40），**未实测**，待 T-005/T-202 | 官方只给出播放器 RTC 缓冲建议 0.2 s / 0.8 s（S2）；端到端延迟 **⚠️ 无一手数据**，待 Phase 2 实测 | **⚠️ 官方文档未给数值**，待实测 |
| 开发成本 | 低～中：小程序 PTT UI、WS 分片、网关中继、Opus；全部在 T-202 范围内 | 高：两端 SDK 接入 + 云端录制/转写旁路 + 与方案 C 双通道降级 | 中～高：HAL、铃声、视频与寄送审核、小程序插件接入；且 1 对 1 来电语义需另做调度逻辑 |
| 运营成本 | 无平台使用费；带宽按 PCM 16 kHz/16 bit 单声道计算为 **256 kbps/方向**（约 57.6 MB/30 分钟/方向），可在网关转 Opus 留存；转写费用见策划书 §11.2 | 旗舰版 **6,250 元/月 ≈ 75,000 元/年**（若需 Linux SDK，S4/S6）；仅小程序侧用基础版 625 元/月 ≈ 7,500 元/年，但无法覆盖狗端 SDK；超量后付费，口径 ⚠️ | 认证费 300 元/年（与所有方案共有）；体验 license 用完后设备 license 套餐收费 **⚠️ 现行规则待微信确认**；寄送设备审核的实物成本 |
| 录音 / 转写 / 审计 | **完整**：音频经云端网关，可落对象存储、可送讯飞实时转写，与策划书「每次对讲可检索、不可篡改」一致 | 🔸 需 TRTC 云端录制或旁路拉流再送转写（套餐含录制计费项，S4）；链路与留存地域待确认 ⚠️ | 🔸 **不可在云端网关完成**：通话媒体经微信后台，文档未提供服务端录音接口；设备侧 HAL 能拿到本端麦克风与对端扬声器 PCM，理论上可在设备侧录制后上传，需微信书面确认合规 ⚠️ |
| 对网络的要求 | 公网 WSS 到自有网关；约 256 kbps/方向；可私有化（D-10） | 公网到腾讯云；UDP/端口与弱网表现待确认 ⚠️ | 公网到微信后台（SDK 会发起网络请求并建立 TLS，S9）；系统时间必须准确 |
| 与铁路专网私有化（D-10、RK-13） | ✅ 可完全私有化 | 🔸 依赖公有云或私有化版本，**⚠️ 是否提供私有化未知** | 🔸 依赖微信后台公网出口，无法私有化 |
| 手机端要求 | 任意基础库 ≥ 2.27.3 | 微信 iOS ≥ 7.0.9 / Android ≥ 7.0.8，基础库 ≥ 2.10.0（S3） | 微信 ≥ 8.0.30（S8） |
| 对 Phase 0 的依赖 | 无 | 小程序主体（B-3）+ 类目通过 + 接口设置开通 | 小程序主体（B-3）+ 类目 + 硬件设备开通 + 实物设备 |

## 4. 对 D-05 的最终建议

### 4.1 建议

**维持 D-05 原文不变**（先做方案 C，再评估 TRTC）。Phase 0 的证据只改变了「评估」的前置条件和成本预期，不改变基线：

- 方案 C 是唯一满足「可录音、可转写、可审计、可私有化、无外部资质依赖」的方案。
- 方案 B 不是「提交一个类目就能上线」：小程序侧（类目/主体）与狗端侧（Linux SDK 申请、旗舰版套餐、aarch64、授权）两道门都要过，任意一道不通则整体不成立。
- 方案 A 的狗端路径已存在（Linux SDK），但它与项目的审计要求和私有化终局冲突，只适合「需要手机微信原生来电强提醒」的补充场景，不适合作为对讲主通道。

### 4.2 升级触发条件（满足全部 ①～④ 且至少一个 ⑤，才启动 T-203）

| # | 条件 | 验证方式 |
|---|---|---|
| ① | 小程序已通过相应类目审核，且后台「开发 › 接口设置」中 live-pusher / live-player **已开通** | 阶段 2 截图 |
| ② | 腾讯云书面确认：Linux SDK 提供 **aarch64（Ubuntu 22.04 / JetPack 6）**构建，可部署在终端设备，并给出授权与计费方式 | 问题清单答复 |
| ③ | 年化成本（含旗舰版套餐）得到业主书面认可 | 业主答复 |
| ④ | 试点与生产网络允许访问腾讯云音视频节点（公网或专线白名单）；若生产为纯铁路专网，须腾讯云确认私有化方案 | 业主 IT / 腾讯云答复 |
| ⑤a | T-202 实测或试点反馈表明半双工 PTT 无法满足作业沟通（例如业主明确要求同时说话） | 现场反馈 |

**降级规则不变**：方案 B 若上线，方案 C 保留为降级通道（与策划书 §3.4 一致）。

### 4.3 方案 A 的触发条件（独立于 B）

仅当业主明确要求「手机微信原生来电 / 强提醒」且接受 §3 中的审计限制，并满足：类目「工具—设备管理」已开通、微信书面确认设备侧录音可行、机载计算单元通过设备唯一性检查。否则不推进。
